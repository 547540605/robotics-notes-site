ROS 2 工程实战 15：MoveIt Servo 与在线速度控制

离线规划回答“从 A 到 B 怎样走”；Servo 回答“此刻请沿这个方向慢慢走”。它是示教、人工微调、视觉纠偏和远程操作的共同底座，但它不是急停，也不是力控制。

本篇唯一闭环：连续 Twist → 连续关节轨迹 → 连续状态反馈

① 上层输入关节速度 / TCP Twist / Pose
② Servo读当前状态、算速度映射
③ 保护限速、奇异/碰撞减速、超时停
④ 输出短时域 JointTrajectory
⑤ 控制器执行并反馈实际状态

与 ROS2-12 的一次性 plan → preview → execute 不同，Servo 在运行中不断读取最新的 joint state 并生成短小轨迹。因此输入一停止或超时，输出就应快速衰减到零，而不是继续沿最后一个速度永远运动。

不可越过的安全边界：MoveIt Servo 的碰撞检查、奇异减速和速度上限是软件层保护，不是人身安全系统。真机上仍必须由厂商控制柜、安全 PLC、急停、保护区、使能策略和现场风险评估承担安全功能。本篇没有真机时，只允许用 RViz / fake hardware 验证语义。

1. 三种输入：同一控制链，不同的人机/算法接口

输入形式消息语义典型来源最容易错的点
Joint jog每关节的速度增量示教按钮、关节微调joint 顺序/单位和实际 robot state 不一致
TCP Twist末端线速度 + 角速度手柄、遥操作、视觉纠偏frame_id 未写清，导致“向前”不是你以为的向前
TCP Pose持续给新的末端位姿目标视觉闭环、上层跟踪器频率、时间戳与姿态容差不适合在线跟随
先只做 Twist。它最能把 3R 的微分运动学复用起来：给定末端瞬时速度 V，系统要构造关节速度 q̇。ROS2-08/09 中的 V = J(q)q̇ 就是这里的数学底座；Servo 把它扩展为六轴、限位、碰撞和控制器接口的工程管线。

2. 速度的“方向”必须先绑定坐标系

错误表述

“让 TCP 向前 2 cm/s。”

它没有说“向前”是 base_link 的 +X、tool0 的 +Z，还是 camera 的光轴方向；机械臂转到不同姿态后，这句话会变成不同运动。

可执行表述

“在 base_link 中给 TwistStamped.linear=(0.02,0,0) m/s，保持 100 ms；或在 tool0 中沿本地 +Z 给同样速度。”

消息的 header.frame_id 与时间戳是命令的一部分，不是可省略注释。

# 概念示例：不是直接可复制的最终启动命令
TwistStamped
  header.frame_id = "base_link"       # 先明确速度在哪个 frame 表达
  header.stamp    = now()
  twist.linear.x  = 0.02              # m/s
  twist.angular.z = 0.00              # rad/s

# 持续输入：例如 50 Hz；停止输入：让 command timeout 接管，输出速度归零。
# 不能把固定速度消息发一次，然后假设机械臂会“聪明地只走一点”。

3. Servo 内部在做什么：把 3R 的 DLS 放进连续工程循环

为了理解而非死记具体源码，可将一次 Servo 更新抽象为：

读状态q、q̇、TF、规划场景
变换命令将 Twist 统一到 planning frame
求关节速度J 的阻尼逆 / 六轴 IK
缩放或停止限位、奇异、碰撞、超时
发短轨迹交给 trajectory controller
# 数学骨架（理解用，不是 MoveIt Servo 源码）
q_dot_raw = J(q).T @ inv(J(q) @ J(q).T + lambda**2 * I) @ V

scale = min(
    velocity_limit_scale(q_dot_raw),
    joint_margin_scale(q),
    singularity_scale(J),
    collision_distance_scale(planning_scene)
)
q_dot = scale * q_dot_raw
q_next = q + q_dot * dt

# 任一输入失效、状态过期或风险策略要求停止：scale → 0。

DLS 的价值是接近奇异时不让 q̇ 无限制放大；代价是末端速度会偏离理想指令。正确的用户体验应是“越来越慢并给出原因”，而不是看似继续精确跟随。

4. 配置不是一份“魔法 YAML”：每个参数回答一个风险问题

参数类别它控制什么验证方式
planning frame / ee frame命令转换所依赖的坐标链同一 Twist 分别在 base/tool 表达，确认运动方向符合预期
publish period / command timeout控制刷新与失联后的停止速度停发输入后记录开始减速和完全停止的时刻
joint velocity/acceleration limits输出轨迹不超 URDF/工程设定对大输入命令检查实际输出是否被钳制
singularity thresholds何时开始减速、何时拒绝继续靠近沿特定姿态逼近，记录 scale 与原因码
collision checking用 Planning Scene 检查预测状态逐渐接近已知 box，观察警告、减速、停止
command output type/topic对接哪个 trajectory controller确认 Servo 输出、controller 接收、joint state 三者关节名一致

5. 建议的跟做顺序：每次只引入一个变量

A. 只启动 fake hardware + joint state broadcaster + trajectory controller：确认 ROS2-13 的 Action 轨迹闭环仍正常。
B. 启动 Servo，但先不开碰撞场景：持续发送低速、固定 frame 的 Twist；验证 TCP 沿预期轴平滑移动，停止消息后能停。
C. 改变机器人姿态：用同一条 base_link Twist 和同一条 tool0 Twist 对比，亲眼确认参考系导致的方向差异。
D. 加一个显眼的 box：让命令指向障碍；记录从正常、减速到停止发生在哪个距离。不要一开始就调所有阈值。
E. 接近已知奇异姿态：观察末端响应会降低，关节速度不会爆掉；结合 ROS2-09 解释它不是“避障”。
F. 最后才接键盘/手柄：输入设备只是命令来源。先用确定的程序消息证明控制链正确，才不会把手柄映射问题误判为运动学问题。

6. 必须会解释的四类“停了”

输入超时

上游停止发布或时间戳过期。期望行为是受控减速至零；检查 command timeout 与消息频率。

关节/速度限位

给定方向会推动某关节接近硬限位，或请求速度过大。期望行为是缩放或停止，不是静默裁剪后假装完成命令。

奇异性接近

Jacobian 条件变坏，一个小 TCP 速度需要巨大关节速度。期望行为是减速/停止并报告奇异原因。

规划场景碰撞

根据模型与当前 Planning Scene，预测路径靠近/进入障碍物。先验证场景 frame、碰撞几何与最新 robot state，再讨论阈值。

本篇完成判据：在 fake hardware 中，你能用带明确 frame_id 的 TCP Twist 连续移动末端；停止输入后它会停；并能分别演示和解释限速、输入超时、奇异减速、碰撞减速。真正的手柄、视觉和真机只是替换上游输入或底层 hardware driver，不改变这条闭环。
