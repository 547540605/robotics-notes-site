ROS 2 全景看板 · ROS2-12：MoveIt 规划场景 · 04–13 路线

ROS 2 工程实战 13：ros2_control、JointTrajectory 与 fake hardware

现在才来到“执行”边界。上篇 MoveIt 产出的是规划结果；本篇解释它如何变成一个可跟踪、可反馈、可报错的关节轨迹请求。先让 fake hardware 跑通，真机驱动以后在同一个边界替换。

一条轨迹下去前，经过的层次

MoveIt / 任意上层应用：产生或选择一条 JointTrajectory，但不直接懂电机协议。
JointTrajectoryController：接收轨迹 Action，检查 joints、时间点、接口与目标，持续输出命令并报告反馈。
controller_manager：装载、激活控制器，保证同一 command interface 不被多个控制器抢占。
ros2_control Hardware Interface：以固定周期 read() 读状态、write() 写命令；fake hardware 或厂商驱动都在这里。
硬件 / fake hardware：前者是实际驱动器与反馈，后者是遵守同一接口的模拟状态，不产生任何物理动作。
修正 ROS2-03 的认知：向 /joint_states 发布内容只会让数字孪生经 robot_state_publisher → /tf → RViz 更新，它不是通用的设备命令接口。需要受控执行时，关节轨迹应交给 controller 的 Action；安全、反馈和中止都需要这条闭环。

1. URDF 中的 ros2_control 标签：声明接口，不替硬件写逻辑

<ros2_control name="SixAxisSystem" type="system">
  <hardware>
    <plugin>mock_components/GenericSystem</plugin>  <!-- 本阶段 fake hardware -->
  </hardware>
  <joint name="joint_1">
    <command_interface name="position"/>
    <state_interface name="position"/>
    <state_interface name="velocity"/>
  </joint>
  <!-- joint_2 ... joint_6 以相同名字和接口声明 -->
</ros2_control>

必须逐字相同的名字

URDF joint、SRDF planning group、controller YAML 的 joint list 与 MoveIt trajectory 中的 joint_names 必须是同一组同一拼写。名字错一个，最危险的情况不是“慢一点”，而是轨迹不能安全映射到目标关节。

interfaces 是能力合同

本阶段以 position command 为例。控制器只能声明并使用硬件实际提供的接口；速度、力矩、GPIO 或状态诊断需要硬件接口明确导出，不能通过“多写一行 YAML”凭空获得。

2. 两个控制器，各做一件事

控制器输入/输出你应该看到什么
joint_state_broadcaster读 hardware state → 发布 /joint_statesRViz、robot_state_publisher、MoveIt 看到一致的当前关节位置
joint_trajectory_controller接 Action trajectory → 输出 joint command；同时反馈 execution state目标/实际/误差随时间更新，成功、取消、容差超限可区分
# controllers.yaml 的语义骨架（名字以实际包为准）
controller_manager:
  ros__parameters:
    update_rate: 100
    joint_state_broadcaster: {type: joint_state_broadcaster/JointStateBroadcaster}
    arm_controller: {type: joint_trajectory_controller/JointTrajectoryController}

arm_controller:
  ros__parameters:
    joints: [joint_1, joint_2, joint_3, joint_4, joint_5, joint_6]
    command_interfaces: [position]
    state_interfaces: [position, velocity]

3. 为什么用 Action，不是只发一条 Topic

FollowJointTrajectory 是有生命周期的请求：客户端发送目标后会收到接受/拒绝，执行中持续收到feedback，结束获得result。这让上层能明确区分“控制器未激活”“目标关节不匹配”“执行被取消”“超出 path/goal tolerance”“按时完成”。

JointTrajectory:
  joint_names: [joint_1, joint_2, joint_3, joint_4, joint_5, joint_6]
  points:
    - positions: [q1a, q2a, q3a, q4a, q5a, q6a]
      time_from_start: 0.0 s
    - positions: [q1b, q2b, q3b, q4b, q5b, q6b]
      time_from_start: 2.0 s

# 不可省略的执行前检查：joints 顺序、时间递增、限位、当前状态、控制器是否 active。

4. fake hardware 的学习顺序：把“看起来在动”和“控制正确”拆开

A. 列出硬件接口与控制器：确认六个 joint 的 position state/command 都存在，两个 controller 均 active。
B. 仅发一个安全 home trajectory：在 RViz 中观察实际 state 跟踪目标；检查 joint 顺序没有错位。
C. 请求取消：验证 Action 结果是 cancelled，状态不会继续假装成功。
D. 故意构造错误请求：例如未知 joint 或 time_from_start 不递增，确认 controller 拒绝而不是悄悄“猜”。
E. 再接 MoveIt：让 ROS2-12 的计划交给同一 controller；观察 planned trajectory、controller feedback、最终 state 三者闭环一致。

5. 真机到来时，哪些不变，哪些必须重做？

保持不变替换/新增
URDF/SRDF 的运动学骨架、planning group、TCP 语义；MoveIt 的目标与规划场景概念；上层 Action 的成功/失败处理。厂商 ROS 2 driver 的 Hardware Interface、网络/现场总线连接、控制器与厂商控制模式的匹配、真实 joint limit/速度限制、时间同步与诊断。
“先 plan、后 preview、确认状态后再 execute”的软件流程。安全回路、急停、使能、保护区、风险评估与现场操作权限。它们不是 fake hardware 阶段能替代或模拟的东西。
本篇验收：你能画出从 MoveIt trajectory 到 hardware write() 的路径；用 fake hardware 让一个受 Action 监测的安全关节轨迹完成；并说明以后接厂商六轴时，为什么是替换 hardware driver 而不是继续向 /joint_states 发数据。至此，3R 基础 → 六轴模型 → MoveIt 规划 → 受控执行的学习闭环建立完成。
