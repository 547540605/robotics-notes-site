ROS 2 工程实战 11：六轴 URDF、SRDF 与 MoveIt 配置

从手写 3R 公式转入工业六轴软件栈。这里不开始“点按钮让它动”，而是先把每份模型和配置的职责切干净：哪份文件描述真实机器，哪份文件只服务规划，哪一层才接控制器。

本篇交付物：RViz 里一台“被正确理解”的六轴机械臂

① URDF/Xacro几何、关节、惯量、碰撞体
② SRDF规划组、TCP、自碰撞例外
③ MoveIt config运动学、规划器、限制
④ ros2_control config接口和控制器名称
⑤ RViz验证模型、TF、规划组

当前没有确定型号的真机，因此使用一个 ROS-ready 的通用六轴模型 + fake hardware。这是为理解标准接口服务，不假装等同于你工作中的任一厂商设备。未来接真机时，替换的是驱动/硬件接口，不是推翻本篇的模型边界。

先划清两件事：URDF 是机器人“物理与运动学事实”的描述；SRDF 是 MoveIt 对这台机器“怎样规划”的补充语义。SRDF 不是 URDF 的替代品，也不会定义连杆长度或关节轴。

1. 先选模型的标准：不是“找一个六轴 STL”就够了

必须具备为什么没有时的后果
6 个连续转动关节可覆盖典型工业臂的关节链和冗余缺失条件不是本阶段要学的六轴 IK/姿态问题
每关节 axis、origin、上下限FK、IK、碰撞与控制器都依赖同一份关节真值RViz 能显示也可能算错、越界
visual 与 collision 几何前者给人看，后者给碰撞检测算只放精细网格会慢；没有 collision 则规划器会“穿模”
base_link、法兰与 tool0/TCP任务目标必须明确相对谁、作用在工具哪里所谓“末端到目标”没有共同含义
可追溯来源与许可后续项目能复现、能替换真实型号模型可能与真机零位、限位不一致

2. URDF/Xacro：只回答“机器是什么”

每一个 link 要有三套信息

  • visual：RViz 画出的外观；
  • collision：规划器使用的简化碰撞体；
  • inertial：质量、质心、惯量，后续动力学与仿真使用。

实操顺序：先用 box/cylinder 把 collision 做正确，再考虑视觉网格美观。细网格不是碰撞模型的默认答案。

每一个 joint 要核对五项

  1. parent/child 是否连成唯一链；
  2. origin 是否是父坐标到关节零位的变换；
  3. axis 是否在 joint 自身坐标中；
  4. limit 的单位是否为 rad、rad/s、rad/s²；
  5. 零位姿态是否和厂商机械图/标定约定一致。
<joint name="joint_3" type="revolute">
  <parent link="link_2"/>
  <child  link="link_3"/>
  <origin xyz="0 0 0.425" rpy="0 0 0"/>
  <axis xyz="0 1 0"/>
  <limit lower="-3.14" upper="3.14" velocity="2.0" effort="80"/>
</joint>

<!-- TCP 是一条固定关节：任务位姿的落点，不是“随便加的红球” -->
<joint name="flange_to_tool0" type="fixed"> ... </joint>

3. SRDF：只回答“MoveIt 要怎样看待这台机器”

planning group

把 joint_1 … joint_6 声明为一个链（或一组 joints），并指定根 base_link 与末端 tool0。之后 Pose 目标、规划请求和控制器映射都以这个组名为入口。

自碰撞矩阵（ACM）

禁用的是结构上永远接触或经大量采样确认不会碰撞的 link pair，例如相邻关节的固定贴合面。绝不是为了让一次失败规划“通过”就把任意碰撞对关掉。

virtual joint

把世界/工位坐标与 base_link 连起来。固定底座通常是 fixed；若机器人在移动底盘上，模型要明确这不是固定关系。

end effector

若有夹爪，可把其 group 附到法兰 link。tool0 是任务 TCP；夹爪模型是工具本体，两者概念不同但可以关联。

4. 配置文件之间怎么接：别把参数塞错地方

文件/组件应放内容不应放内容
robot.urdf.xacro连杆、关节、几何、惯量、ros2_control 标签规划器算法、工作台障碍物
robot.srdfgroup、TCP、ACM、虚拟关节关节轴、真实限位数值
kinematics.yaml每个 group 的 IK solver、超时与搜索参数把解析 IK 公式复制进 YAML
joint_limits.yaml规划时采用的速度/加速度缩放上限突破 URDF 的硬件限位
controllers.yaml状态广播和轨迹控制器的名字、joints规划场景碰撞物

5. 逐步验收：每一步过了才进入下一步

A. 只启动 robot_state_publisher + joint_state_publisher_gui：关节滑块运动时，六轴每一段转轴都符合预期；TCP 没有飘。
B. 加 RViz RobotModel + TF：能看到 world → base_link → … → tool0 的完整链；没有断开的 frame。
C. 加 MoveIt RViz 插件：Planning Group 下拉框能选到 arm；交互 marker 落在 tool0，而非某个中间法兰。
D. fake hardware + controller：状态显示与控制器 joints 顺序一致。这里只证明接口正确，尚未证明任何真机能动。
本篇完成的判据：你能指着任意一项说清它属于 URDF、SRDF、MoveIt 参数，还是控制器参数；并且 RViz 中的零位、关节轴、TCP、planning group 四者彼此一致。下一篇才让 move_group 结合这些信息做位姿规划。
