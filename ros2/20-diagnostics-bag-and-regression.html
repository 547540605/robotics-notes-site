ROS 2 工程实战 20：诊断、rosbag、回归与部署

一个机械臂系统真正难的时刻，往往不是“第一次跑通”，而是某次现场偏了、卡了、超时或中断后，谁也说不清当时的状态。诊断和回归的目标是让问题变成可证据化、可复现、可验证修复的对象。

排障闭环：先拿证据，再提出假设，再回放验证

① 观测状态、TF、I/O、action、诊断
② 关联统一时间戳与 cycle/目标 ID
③ 留存rosbag + 配置版本 + 日志
④ 回放在隔离环境复现
⑤ 回归确认修复且未破坏旧行为

“日志里看到报错”不是诊断完成；“把报错压掉了”更不是修复。每一次异常至少要能回答：何时发生、当时机械臂在哪、目标是什么、哪个状态/控制器/I/O 首先异常、修复后用什么证据验证。

1. 最小证据集：不是所有 topic 都录，也不能只录一行文本

类别建议留存能回答的问题
机器人状态/joint_states、控制器状态、硬件/驱动状态实际关节在哪、跟踪误差何时出现、设备是否已失效
坐标与环境/tf、/tf_static、目标 Pose、Planning Scene 版本目标在哪个 frame、变换是否缺失/过期、障碍物当时是否存在
任务与动作state transition、cycle ID、Action goal/feedback/result、错误码系统处于哪一步、规划成功还是执行失败、何时取消
外部设备关键 I/O、相机时间戳/CameraInfo、传感器质量/置信度工件/夹具/视觉是否真正满足 guard
配置身份机器人模型、TCP/workpiece 标定版本、参数文件版本、软件提交版本这次运行究竟用的是哪套模型与限制
隐私与容量：rosbag 会迅速变大，也可能包含现场图像、工件信息或网络信息。录制策略必须定义主题白名单、保留周期、脱敏/访问权限和异常触发保存规则；不要默认把所有内容长期落盘。

2. 时间戳与 ID：让分散消息能被拼回同一次事件

时间戳

每条关键日志都带 ROS 时间和系统/设备时间来源。对视觉、TF、joint state 与动作反馈，优先使用消息自带 timestamp；“日志打印顺序”不能证明物理事件先后。

关联 ID

为每个 cycle、目标、规划请求、Action goal 生成/传递 ID。故障报告中写 “goal 42 在 state EXECUTE、目标 frame=workpiece_7、控制器 result=ABORTED”，比“今天下午偶尔失败”可排查得多。

# 结构化日志示意：字段比一句自然语言更重要
event="trajectory_result"
cycle_id="2026-...-0017"
goal_id="..."
state="EXECUTE_PREAPPROACH"
result="ABORTED"
robot_state_age_ms=18
target_frame="workpiece_frame"
tcp_calibration_version="tcp-v3"

# 记录原因和上下文；不要把整套关节/图像数据塞进 console 文本。
# 大数据进入 bag，小而关键的索引信息进入结构化事件日志。

4. rosbag 回放不是“录了就能复现”

回放适合复现数据流与算法决策；它不自动复现真实硬件时序、网络延迟、控制柜安全状态或物理接触。要让回放有价值，先固定它的目的：

离线算法回归

将 bag 中的传感器/TF/状态输入重放给定位、规划前检查或状态机逻辑；断言输出目标、错误分类、状态转换与预期一致。最适合视觉、TF、规则和故障分支。

系统集成回归

用 fake hardware、固定模型和 mock I/O 启动整套 launch；验证 controller active、规划请求、Action 结果、状态机回退等接口契约。它仍不替代真机验收。

一次 bug 修复的最低验收格式：
1. 保存可复现输入（bag / mock 输入 / 参数版本）
2. 写明原来错误的可观测结果（例如：过期 TF 仍被接受）
3. 修改逻辑
4. 重放同一输入，断言新结果（例如：过期 TF 被拒绝并进入 FAULT）
5. 运行已有的 happy-path 回归，确认正常 cycle 未受影响

5. 部署不是“复制 workspace”：配置、启动和回滚都要可控

A. 参数外置：机器人型号、IP/端口、TCP、工件 frame、速度缩放、超时、I/O 映射不硬编码进业务节点；每套工位配置有名字和版本。
B. 启动分层：模型/TF、驱动/控制器、MoveIt、感知、任务状态机分开启动并报告 readiness；任务层不应在底层尚未 ready 时抢跑。
C. 健康检查：检查 hardware/controller lifecycle、joint state 新鲜度、关键 TF、相机/传感器、磁盘空间和时间同步；将“不健康”转换为明确不可执行状态。
D. 变更可回滚：每一次参数或代码改动要关联版本、验收记录和可恢复的旧配置；现场不能只靠“我记得上个版本大概能跑”。
E. 报警可行动：告警正文必须给出受影响对象、状态、时间、建议下一步和相关 bag/log 的定位，而不是只写 error code。

6. 给自己建立一张故障单模板

标题： [执行] arm_controller 在预接近阶段 ABORTED
影响： cycle 被安全中止；未进入工艺动作
复现输入： bag / mock 场景 / 配置版本 / 软件版本
时间线： t0 state=PLAN；t1 action accepted；t2 joint error 超阈值；t3 ABORTED
证据： goal_id、controller state、joint state 曲线、TF/scene 版本
根因假设： ...
修复： ...
验证： 原始输入回放 + happy-path 回归 +（真机时）批准的低风险验证
遗留风险： ...
本篇完成判据：你能为一次“规划成功但执行失败”的事件列出需要录制的证据；能用固定输入回放证明一个 bug 被修复；并能解释为什么 controller、MoveIt、视觉、状态机和配置版本必须通过时间戳与 ID 关联，而不能靠肉眼翻日志。
